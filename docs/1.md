UI 交互与底层数据结构的系统设计方案。

### 一、 核心判断：关于“标题/业务品类”的价值

**结论：品类与业务标签对系统不仅有益，而且是未来模型迭代的核心资产，绝不能采用“随机数”敷衍过去。**

在计算机视觉中，不同品类服装的空间形变规律完全不同（例如：百褶裙的纹理形变与硬挺的牛仔夹克有本质区别）。如果 `img-dc` 模型在评测时得分很低，你必须知道它到底是在“大衣”上翻车了，还是在“碎花裙”上翻车了。
如果没有品类标签，你的数据集将是一个黑盒，无法进行针对性的弱点分析（Hard Example Mining）和定向微调。

### 二、 UI/UX 交互设计（主打“无痛丝滑”）

为了做到真正的无痛，前端交互必须消除反复打字和文件管理的摩擦感。

**1. 设计师身份识别（零登录摩擦）**
* **设计：** 摒弃繁琐的账号密码注册。首次打开页面时，弹出一个极其简单的对话框：“请选择/输入你的花名”。输入后，前端通过 `LocalStorage` 永久记住该身份。
* **交互：** 页面右上角显示当前设计师头像/名字，支持点击切换（防止换人用电脑）。后续每次打开直接进入上传界面，完全无感。

**2. 任务上下文（标题与品类）**
* **设计：** 将自由输入的“标题”降级为可选备注，将“品类/业务”升级为**点击即选的快捷标签库**（Tagging System）。
* **交互：** 提供两排按钮，例如第一排是业务线（“春季女装”、“大促款”、“男装”），第二排是物理品类（“上衣”、“裤装”、“连衣裙”、“配饰”）。设计师只需鼠标点选两个 Tag，即可完成高质量的元数据标注。

**3. 核心工作区：四格沉浸式拖拽槽**
* **设计：** 页面主体被划分为 4 个宽大的图片卡槽。
    * 卡槽 1（必填）：`👗 原始商品图 (Reference)`
    * 卡槽 2（必填）：`🤖 试穿生成图 (Try-on)`
    * 卡槽 3（必填）：`✨ 完美精修图 (Retouched)`
    * 卡槽 4（可选）：`⭕ 涂鸦标注图 (Visual Prompt) - 可空`
* **交互细节（丝滑的关键）：**
    * **全局拖拽感知：** 支持设计师直接框选本地的 3-4 张图，**一次性拖入浏览器**。
    * **快捷键支持：** 支持在选定某个卡槽时，直接通过 `Ctrl+V / Cmd+V` 从剪贴板粘贴图像（设计师经常在通讯软件或画图工具中直接截图，要求他们先保存为文件再上传是非常反人类的）。

### 三、 系统数据结构设计（Ingestion 摄入层）

当前 `img-dc` 的 `data/product` 和 `data/tryon` 这种扁平化目录结构适合模型训练，但不适合原始数据的收集与追溯。我们需要在后端设计一个“原始数据摄入层（Raw Ingestion Area）”。

每次设计师点击“提交”，后端不应直接把图散落到各个训练目录，而是生成一个包含独立 UUID 的任务包（Task Bundle）。

**存储结构示例：**
```text
/data/raw_ingestion/
  ├── <UUID_1>/
  │   ├── product.jpg
  │   ├── tryon.jpg
  │   ├── retouched.jpg
  │   ├── annotated.jpg  (如果有)
  │   └── metadata.json
  └── <UUID_2>/
      ├── ...
```

**metadata.json 结构示例：**
```json
{
  "task_id": "uuid-xxxx-xxxx",
  "designer_id": "张三",
  "upload_time": "2026-05-04T10:00:00Z",
  "business_line": "春季女装",
  "category": "连衣裙",
  "optional_notes": "领口 AI 画反了，很难修",
  "has_annotation": true
}
```

**后端路由逻辑：**
后端（如 FastAPI）接收到这个 Bundle 后，除了原样落盘保存至 `raw_ingestion` 目录外，再通过后台定时任务或事件触发，将图片按规则软链接（Symlink）或复制到 `img-dc` 训练所需的 `data/product` 和 `data/tryon` 目录中，并自动执行精修图与试穿图的相减计算，生成 Mask 存入 `data/annotations`。
